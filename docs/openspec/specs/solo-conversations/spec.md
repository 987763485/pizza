# solo-conversations Specification

## Purpose
定义单智能体会话的核心行为：用户消息如何被路由给绑定智能体、流式输出如何呈现、运行如何停止和重试，以及附件和失败状态如何可靠保存。

## Requirements

### Requirement: 创建单智能体会话

本要求为强制要求（MUST）。

用户从首页或参与者选择器选择一个智能体后，系统必须创建一个绑定该智能体和工作区的单智能体会话。会话标题取首条用户消息的前 24 个字符并允许后续重命名。

#### Scenario: 从首页发送首条消息

- **WHEN** 用户选择一个智能体、输入消息并发送
- **THEN** 系统创建新会话并将会话标题设为消息前 24 个字符
- **AND** 输入框路由提示显示该智能体的名称

#### Scenario: 没有可用智能体

- **WHEN** 用户尚未创建任何智能体
- **THEN** 首页参与者选择器显示创建智能体的入口
- **AND** 发送操作被阻止并说明需要先创建智能体

### Requirement: 单智能体消息路由

本要求为强制要求（MUST）。

单智能体会话中，用户未显式提及其他目标的消息必须发送给会话绑定的智能体。单智能体模式下不得产生跨智能体调度。

#### Scenario: 默认路由

- **WHEN** 用户在单智能体会话中发送一条未包含提及的消息
- **THEN** 该消息只触发绑定智能体的一次运行
- **AND** 会话中不出现其他智能体

#### Scenario: 模式二智能体的单智能体兜底

- **WHEN** 指令来源为 `leader` 的智能体在没有指挥者下发指令的单智能体会话中运行
- **THEN** 使用可选兜底 Prompt，留空时使用通用兜底 Prompt
- **AND** 不因初始 Prompt 为空而失败

### Requirement: 流式输出

本要求为强制要求（MUST）。

智能体运行时，界面必须逐段呈现文本增量，并显示头像、名称、运行状态和耗时。首字延迟受运行时限制，但界面必须在运行开始后立即显示可辨认的进行中状态。

#### Scenario: 流式文本

- **WHEN** 运行时返回文本增量
- **THEN** 消息内容逐步增长且不闪烁或丢失已显示内容
- **AND** 消息头部显示运行中的状态

#### Scenario: 流式过程中切换页面

- **WHEN** 用户在运行中切换到设置或另一个会话
- **THEN** 原运行继续执行
- **AND** 返回会话时可以看到完整或最新的已接收内容

### Requirement: Markdown 与工具调用展示

本要求为强制要求（MUST）。

智能体消息必须支持标题、列表、表格、代码块、链接和任务列表渲染。工具调用必须以可折叠行展示名称、参数摘要、状态和耗时；失败的工具调用必须显示错误且可展开查看。

#### Scenario: 渲染代码块

- **WHEN** 智能体输出包含代码块的消息
- **THEN** 代码块保留缩进和语法高亮
- **AND** 用户可复制代码内容

#### Scenario: 工具调用失败

- **WHEN** 运行时报告某个工具调用失败
- **THEN** 该调用行标记为失败并自动展开错误摘要
- **AND** 消息其他内容保持可见

### Requirement: 停止运行

本要求为强制要求（MUST）。

用户必须能够停止当前单智能体运行。停止后界面应在两秒内显示已停止状态，保留已接收内容，并插入一条弱化的系统事件说明用户停止了运行。

#### Scenario: 用户停止生成

- **WHEN** 用户在智能体流式输出时点击停止
- **THEN** 当前运行在界面中变为已停止
- **AND** 已显示的内容保留且可以继续发送新消息

### Requirement: 重试失败或停止的消息

本要求为强制要求（MUST）。

用户必须能够重试失败或被停止的智能体回复。重试必须创建新的运行，不得删除原消息，也不得把原运行的已接收内容重复计入新运行。

#### Scenario: 重试失败回复

- **WHEN** 用户对一条失败回复点击重试
- **THEN** 系统创建新的运行并重新请求智能体
- **AND** 原失败消息保留在会话中并有独立状态

### Requirement: 运行中继续输入

本要求为强制要求（MUST）。

智能体运行中，输入框必须保持可用。用户发送的新消息在运行时支持追加时可以直接注入，否则必须进入队列，并在界面明确显示「已排队」或「已插话」状态。

#### Scenario: 运行中排队

- **WHEN** 运行中的运行时不支持追加输入且用户发送新消息
- **THEN** 新消息显示为已排队
- **AND** 当前运行结束后自动处理该消息

### Requirement: 附件输入

本要求为强制要求（MUST）。

用户必须能够通过按钮、拖拽或粘贴添加图片、文本和代码文件作为附件。单个文件不得超过 20 MB；附件必须随消息持久化，并可在消息中预览或下载。

#### Scenario: 添加图片附件

- **WHEN** 用户拖入一张不超过 20 MB 的图片并发送
- **THEN** 消息中包含可预览的图片附件
- **AND** 重启应用后附件仍可打开

#### Scenario: 超过附件大小限制

- **WHEN** 用户添加超过 20 MB 的文件
- **THEN** 应用拒绝该文件并显示大小限制
- **AND** 其他已添加附件不受影响

### Requirement: 消息持久化与失败恢复

本要求为强制要求（MUST）。

用户消息和智能体消息必须在生成和接收过程中可靠落库。发送失败时，用户草稿和已输入内容不得丢失；运行失败时必须显示失败原因、重试入口和查看日志的入口。

#### Scenario: 发送失败保留草稿

- **WHEN** 消息因本地存储或运行时错误未能发送
- **THEN** 输入框保留用户原始内容
- **AND** 界面提供重试操作

#### Scenario: 失败原因可见

- **WHEN** 一次运行以错误结束
- **THEN** 消息显示具体错误摘要
- **AND** 用户可以展开查看脱敏后的运行日志
