# team-orchestration Specification

## Purpose
定义团队回合如何排队、并发、等待、介入和收敛，并通过可配置的保护阈值避免无限互 @、重复调用和成本失控。

## Requirements

### Requirement: 团队回合队列

本要求为强制要求（MUST）。

每个团队会话必须维护独立的调度队列。同一智能体同一时刻只能处理一个运行；同一会话的多个运行必须按队列和并发上限调度，不得因 UI 操作重复入队。

#### Scenario: 同一智能体重复入队

- **WHEN** 同一智能体在已有运行未结束时再次被提及
- **THEN** 新任务进入队列而不并行启动
- **AND** 当前运行结束后只处理一次新任务

### Requirement: 指挥者主导的调度

本要求为强制要求（MUST）。

只有用户和指挥者可以发起成员调度。指挥者精确提及成员时，编排器向该成员下发一个单轮任务 Prompt；成员完成后结果回到调用者或指挥者。成员消息中的其他成员提及不得直接触发调度，必须作为建议随结果交回指挥者，由指挥者决定是否派发。编排器不得按固定轮次自动唤醒成员，也不得要求每轮所有成员发言。

#### Scenario: 成员提及其他成员

- **WHEN** 成员在回复中精确提及其他团队成员
- **THEN** 编排器不直接启动被提及成员
- **AND** 该提及随成员结果交回指挥者，由指挥者决定后续派发

#### Scenario: 用户直接提及成员

- **WHEN** 用户在团队会话中精确提及某成员
- **THEN** 该成员按用户消息调度
- **AND** 指挥者收到被动通知，但不自动运行

### Requirement: 参与者能力登记

本要求为强制要求（MUST）。

编排器必须在指挥者的上下文中提供完整的参与者能力目录：名称、能力描述、团队职责、指令来源与当前运行状态。指挥者像选择 Skill 一样，根据任务与能力描述的匹配度自主决定何时 `@` 哪位成员，不得按固定顺序或轮次强制派发。子智能体只完成被分派的单轮任务并回传结果，不得跨子智能体直连。

#### Scenario: 按能力选择成员

- **WHEN** 指挥者收到一个需要架构评估的任务
- **THEN** 它根据能力描述选择具备架构评估能力的成员
- **AND** 不派发能力不匹配的成员

#### Scenario: 子智能体回传结果

- **WHEN** 成员完成被分派的单轮任务
- **THEN** 结果回到指挥者
- **AND** 成员不直接调度或汇总其他成员

#### Scenario: 按运行状态避免重复派发

- **WHEN** 某成员已有运行或已在派发队列中
- **THEN** 指挥者上下文中该成员标记为运行中或排队中
- **AND** 编排器不为该成员重复创建运行

### Requirement: 指挥者动态下发角色指令

本要求为强制要求（MUST）。

指令来源为 `leader` 的团队成员运行时，编排器不得注入该成员保存的 Prompt 或团队 Prompt 覆盖，必须把触发这次运行的消息作为本轮角色指令。指挥者的能力目录必须标注成员的指令来源；对模式二成员，指挥者 `@` 时必须提供角色、职责边界、输出格式与完成标准。指挥者自身始终使用自己的 Prompt；没有指挥者下发的场景使用可选的单智能体兜底 Prompt，留空时使用通用兜底 Prompt。

#### Scenario: 模式二成员使用动态指令

- **WHEN** 指挥者 `@` 一名指令来源为 `leader` 的成员并要求其以特定角色完成任务
- **THEN** 该成员的运行上下文包含本轮角色指令
- **AND** 不包含该成员保存的 Prompt 与团队覆盖

#### Scenario: 指挥者识别动态指令成员

- **WHEN** 指挥者读取参与者能力目录
- **THEN** 每名成员标注「自带 Prompt」或「指挥者动态下发」
- **AND** 对动态下发成员按协议写清角色、边界、输出格式与完成标准

#### Scenario: 单智能体运行兜底

- **WHEN** 指令来源为 `leader` 的智能体在没有指挥者下达指令的单智能体会话中运行
- **THEN** 使用可选兜底 Prompt，留空时使用通用兜底 Prompt
- **AND** 不因初始 Prompt 为空而失败

### Requirement: 并发上限

本要求为强制要求（MUST）。

团队会话默认最大并发运行数为 3，并允许在团队配置范围内调整。达到上限时，新运行必须排队并显示排队状态，不得静默丢弃。

#### Scenario: 五个成员同时被提及

- **WHEN** 指挥者一次性精确提及五名成员
- **THEN** 最多三个运行同时开始，其余两个排队
- **AND** 界面显示每个成员的运行或排队状态

### Requirement: 并行与串行策略

本要求为强制要求（MUST）。

团队必须支持并行和串行两种扇出策略。并行时多个成员同时开始；串行时按提及顺序执行，后一个成员必须能看到前一个成员的结果。P0 使用团队配置的默认策略，不解析自然语言指令。

#### Scenario: 并行扇出

- **WHEN** 团队默认策略为并行且指挥者提及三名成员
- **THEN** 三名成员可以同时开始运行
- **AND** 结果分别返回指挥者

#### Scenario: 串行扇出

- **WHEN** 团队默认策略为串行且指挥者按顺序提及三名成员
- **THEN** 成员按提及顺序依次运行
- **AND** 后一个成员上下文包含前一个成员的结果

### Requirement: 用户插话

本要求为强制要求（MUST）。

团队运行中用户必须能够发送消息，输入框不得被阻塞。会话级插话模式为「排队」时，消息在当前运行结束后送达；为「立即插话」且运行时支持追加输入时，消息注入当前运行并标记为已插话，否则降级为排队并明确提示。

#### Scenario: 排队插话

- **WHEN** 团队运行中用户发送一条消息且会话为排队模式
- **THEN** 消息显示为已排队
- **AND** 当前运行结束后该消息送达指定目标

#### Scenario: 立即插话降级

- **WHEN** 用户选择立即插话但运行时不支持追加输入
- **THEN** 消息转为排队并显示降级提示
- **AND** 不中断当前运行

### Requirement: 停止运行

本要求为强制要求（MUST）。

用户必须能够停止单个运行或本回合全部运行。停止后两秒内界面必须显示已停止状态，保留已产生内容，并插入说明停止目标的系统事件。其他未停止运行不得被误取消。

#### Scenario: 停止单个成员

- **WHEN** 用户在多名成员运行时停止其中一名成员
- **THEN** 只有该成员的运行被取消
- **AND** 其他成员继续运行

#### Scenario: 停止全部

- **WHEN** 用户点击全部停止
- **THEN** 本回合所有运行进入已停止状态
- **AND** 会话不再调度新的运行直到用户再次发送消息

### Requirement: 循环与成本保护

本要求为强制要求（MUST）。

团队回合必须受以下默认保护：单回合最大跳数 64（团队可配置 1–100，仅用于防止 @ 循环失控）、单运行超时 30 分钟、重复调用抑制开启、A→B→A 连续三次且无新信息时插入收敛提示。团队不设辩论轮次上限。团队 token 预算可选择配置；达到 80% 时提醒，达到 100% 时停止。

#### Scenario: 达到最大跳数

- **WHEN** 单回合调度跳数达到团队配置的上限（默认 64）
- **THEN** 编排器停止调度并让指挥者输出阶段性总结
- **AND** 会话标记为因保护阈值收敛

#### Scenario: 重复调用抑制

- **WHEN** 同一发送者在两分钟内重复向同一目标发送高度相似且无新信息的内容
- **THEN** 该次调用被抑制
- **AND** 审计记录抑制原因

#### Scenario: 达到 token 预算

- **WHEN** 团队回合 token 使用达到配置预算的 100%
- **THEN** 所有新调度停止
- **AND** 会话显示预算耗尽与当前进展

### Requirement: 指挥者协议

本要求为强制要求（MUST）。

团队必须内置指挥者协作协议：第一轮拆解并分派，第二轮起交叉引用具体观点，至少保留反方角色，需要用户决策时精确提及用户，满足收敛条件时输出结构化总结。成员配置不得覆盖该协议。

#### Scenario: 第一轮分派

- **WHEN** 指挥者收到用户的新任务
- **THEN** 它先复述目标并拆解为可分派的子问题
- **AND** 通过精确提及分派给相关成员，而不是代替成员作答

#### Scenario: 需要用户决策

- **WHEN** 指挥者遇到无法从团队信息推断的决策
- **THEN** 它精确提及用户并提出一个具体问题
- **AND** 回合进入等待用户状态

### Requirement: 收敛与总结

本要求为强制要求（MUST）。

团队回合在连续无新论据或指挥者判定收敛时，必须进入收敛状态。指挥者必须输出包含结论、关键依据、分歧与未决问题、建议下一步的 Markdown 总结，并保存为工作区 `.pizza/artifacts/` 产出物。

#### Scenario: 指挥者判定收敛

- **WHEN** 指挥者不再派发成员并输出总结
- **THEN** 回合进入收敛并完成
- **AND** 指挥者输出结构化总结

#### Scenario: 保存收敛产出物

- **WHEN** 指挥者完成收敛总结
- **THEN** 总结保存到 `.pizza/artifacts/` 并出现在产出物面板
- **AND** 会话标记为已完成

### Requirement: 异常与恢复

本要求为强制要求（MUST）。

运行时失败、断线或应用崩溃时，编排器必须把受影响的运行标记为失败或中断，保留已完成成员的结果，并允许用户重试或继续收敛。不得自动重放用户未确认的运行。

#### Scenario: 成员运行失败

- **WHEN** 一名成员在团队回合中运行失败
- **THEN** 该成员标记为失败并保留错误摘要
- **AND** 其他成员结果和指挥者仍可继续处理

#### Scenario: 应用崩溃后恢复

- **WHEN** 应用在团队回合运行中崩溃后重启
- **THEN** 未完成的运行显示为中断
- **AND** 用户可以看到已完成结果并选择重试
