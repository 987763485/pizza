# Design

## Context

本 change 建立在已归档的 `p0-solo-vertical-slice` 之上。单智能体切片已经交付 Electron 主进程、SQLite 仓储、运行时适配器、IPC、流式消息、停止/重试和产出物索引。团队编排必须复用这些基础，不新增第二套消息或运行时通道。

团队模式新增的核心是调度：一条用户消息可能触发多个运行，成员回复又可能触发指挥者或其他成员。调度状态必须可恢复、可审计，并且能在用户插话或停止时安全收敛。

## Goals / Non-Goals

**Goals:**

- 在现有会话模型上增加团队、成员、提及和回合概念，不破坏单智能体数据。
- 把运行时执行与调度分离：单智能体和团队共享同一个执行器，各自管理队列。
- 让 `@` 解析成为独立、可测试、主进程与渲染层共用的纯逻辑。
- 让并发、插话、停止、保护和收敛在应用重启后仍可解释。
- 用回合事件驱动团队对话和对话轨迹，避免 UI 自己推断状态。

**Non-Goals:**

- 团队快照、从快照恢复、动态指令来源模式二、`@全体`、自然语言并行/串行声明。
- Skill/MCP 的实际注入与审批；成员覆盖字段只保留结构，能力管理由后续变更实现。
- 跨团队自动编排、云端协作、移动端。
- 所有运行时的运行中追加能力；P0 不支持的运行时统一降级为排队。

## Decisions

### 1. 共享 AgentRunExecutor，调度器分离

从现有 `RunService` 中抽出 `AgentRunExecutor`，只负责一次运行：

- 打开运行时会话、发送 Prompt、消费标准化事件。
- 更新运行、消息、用量和工具事件。
- 扫描产出物、处理失败和取消。
- 返回结构化运行结果（状态、文本、用量、错误）。

`RunService` 保留单智能体会话的 FIFO 队列和现有公开 API；新增 `TeamOrchestrator` 负责团队队列、并发、回合状态和保护，并调用同一个执行器。执行器不决定会话状态或队列顺序，也不直接驱动 UI。

未选择：让 `TeamOrchestrator` 直接调用现有 `RunService.send`（会把单智能体队列与团队调度混在一起，`isSessionActive` 等假设失效）；新增独立运行时服务进程（重复 IPC 和进程监督，首个团队版本不划算）。

执行器抽取必须先以现有 22 个单元/集成测试和 Electron E2E 回归，保持 `RunService` 公共行为不变。

### 2. 数据模型扩展

新增迁移：

- `team`：工作区、名称、描述、头像、指挥者、编排 Prompt、扇出策略（`parallel|serial`）、最大并发（默认 3）、最大轮次（默认 5）、最大跳数（默认 12）、token 预算（0 表示不限）、归档状态、最近使用时间、创建/更新时间。
- `team_member`：团队、智能体、排序、角色描述、Prompt 覆盖模式（`inherit|append|replace`）与内容、Skill/MCP 覆盖 JSON。成员只能是智能体，P0 不支持团队嵌套。
- `message_mention`：消息、目标类型（`agent|user|unknown`）、目标智能体、显示名称、起止位置、原始语法、是否解析成功。
- `team_turn`：会话、回合序号、状态、触发消息、指挥者、开始/结束时间、收敛原因、跳数、轮次、token 统计、错误。
- `team_turn_event`：回合、序号、事件类型、参与者、运行、负载 JSON。
- `session` 增加 `interjection_mode TEXT NOT NULL DEFAULT 'queue'`。
- `run` 增加 `team_turn_id` 可空外键；现有 `parent_run_id` 和 `trigger_message_id` 继续用于调用链。

回合状态：`dispatching → debating → waiting_user → converging → completed`，另有 `failed | cancelled | interrupted`。状态转换由主进程串行化，非法转换拒绝写入。

团队引用循环：当前成员只能是智能体，不存在团队嵌套；校验器保留团队引用的未来扩展点，并验证指挥者/成员/重复成员等当前模型可表达的不变量。

### 3. 提及解析为共享纯函数

新增 `src/shared/mentions.ts`：

- `serializeMention(agent)` 生成 `[@名称](mention://agent/<id>)`，用户提及生成 `mention://user`。
- `parseMentions(content, mode)` 返回目标、未知、歧义、自引用和展示片段。智能体消息只识别精确链接；用户消息同时识别 chip 序列化与文本 `@名称`。
- 解析顺序：本会话精确名称 → 本团队内名称 → 全局唯一名称。重名且无稳定标识时不猜测，返回歧义；未知目标保留原文并写系统提示。
- 同一目标去重；自身提及忽略并写 `team_turn_event`。
- 消息发送时把解析结果写入 `message_mention`，位置与原始语法一并保存。

### 4. 团队会话与回合

- `SessionService.createTeam(workspaceId, teamId)` 创建 `mode='team'`、`teamId` 设置的会话；`agent_id` 为空，指挥者从团队读取。
- `SessionDetail` 扩展 `team`（含指挥者和成员）与 `participants`，消息按 `senderAgentId` 解析身份；现有 `agent` 字段对单智能体保持兼容。
- 每次用户消息在当前无活跃回合时创建 `team_turn`，`seq` 递增，`roundNo` 与回合序号一致。
- 回合事件类型：`turn_started`、`dispatch`、`run_started`、`run_completed`、`run_failed`、`run_cancelled`、`user_interjection`、`waiting_user`、`protection_triggered`、`converging`、`turn_completed`、`turn_failed`、`turn_cancelled`、`turn_interrupted`。
- 主进程在事件落库后通过新的 `event:team` 推送；渲染层只消费事件和查询结果。

### 5. 调度、并发与再触发

`TeamOrchestrator` 每个团队会话维护一个串行状态机和内存队列：

- 同一智能体同时最多一个运行；不同智能体受团队最大并发限制，默认 3，范围 1–10，并受全局并发设置约束。
- 并行：一次提及的多个成员同时启动；串行：按提及顺序执行，后一个成员上下文包含前一个成员结果。
- 用户未提及：默认指挥者；直接提及成员：只调度成员，并向指挥者写被动通知；提及用户：回合进入 `waiting_user`。
- 成员完成且无显式提及：回复调用者；调用者是指挥者或用户时回到指挥者，调用者是其他成员时回到该成员。成员显式提及其他成员时只调度这些成员，不额外唤醒指挥者。
- 指挥者自己的发言不触发自身。
- 队列项、并发计数器和取消令牌由调度器持有；数据库中的 `run` 与 `team_turn_event` 是恢复和审计的事实来源。

### 6. 插话、停止与恢复

- 用户消息进入会话级 `interjection_mode`：P0 默认 `queue`；`immediate` 仅在运行时声明追加能力时注入当前运行，否则降级为排队并写系统事件说明原因。
- 排队消息保存为普通用户消息并在消息流显示“已排队/送达目标”；当前运行结束后由调度器按目标送达。
- `stop(runId)` 只取消单个运行；`stopTurn(turnId)` 取消本回合所有运行，保留已产生文本，标记回合 `cancelled`，停止新调度。
- 应用启动时把未完成运行标记为中断，把非终态回合标记为 `interrupted`；不自动重放，用户可查看已完成结果并选择重试。

### 7. 上下文组装与压缩

`TeamContextBuilder` 为每次运行构造：

- 系统协作协议（团队规则、精确提及语法、禁止代替成员作答）。
- 当前任务、调用者说明、成员有效配置（继承/追加/替换后的 Prompt）。
- 团队名单（名称、角色、ID）、最近消息、串行前序结果、能力清单、工作区与产出物路径。
- 指挥者再触发时，额外注入自上次指挥者发言以来的成员摘要与关键原文。

压缩采用确定性结构化摘要：保留当前任务、未决问题、决策、参与者结论和产出物路径，截断旧正文；不额外调用模型。原始消息始终保留在数据库。

### 8. 保护与收敛

每次入队前检查：

- 单回合跳数 ≤ 12。
- 辩论轮次 ≤ 团队配置（默认 5）。
- 单运行超时 30 分钟。
- 同一发送者到同一目标、内容高度相似且在 2 分钟内重复时抑制。
- A→B→A 连续三次且无新信息时插入收敛提示。
- token 预算可配置，默认 0（不限）；非零时 80% 提醒，100% 停止新调度。

保护触发必须写 `team_turn_event` 并在消息流显示系统事件；达到跳数/轮次/预算时，调度器把回合置为 `converging`，向指挥者投递“停止辩论并输出结构化总结”的收敛 Prompt。若指挥者失败，主进程生成包含当前进展的系统消息。

收敛总结必须包含结论、关键依据、分歧与未决问题、建议下一步。主进程将其写入 `.pizza/artifacts/team-turn-<seq>.md` 并索引到产出物面板；写入失败时保留会话内完整文本并显示路径与原因。

### 9. UI 扩展

- 设置中的「智能体团队」升级为列表 + 整页编辑器：基本资料、指挥者/成员、成员覆盖、编排 Prompt、最终生效预览。
- 头脑风暴模板：用户选择运行时后，自动创建缺失的五个内置角色智能体（主持人、产品经理、架构师、唱反调者、用户研究员），再创建可编辑团队。
- 首页参与者下拉增加「智能体团队」分组；选择团队创建团队会话。
- 团队会话复用三栏外壳：团队头部（头像堆叠、指挥者、成员数）、回合分隔、多参与者消息头、指挥者/成员标签、等待用户卡片、单个/全部停止、插话状态。
- 输入框使用轻量 contentEditable 提及编辑器：`@` 打开分组选择器（指挥者/成员/我），插入不可编辑 chip，发送时序列化为精确提及语法；消息气泡把 mention 链接渲染为 chip。
- 右侧面板增加「对话轨迹」页签，读取 `team_turn_event` 展示参与者、分派、辩论、插话、停止和收敛；收敛产出物出现在产出物页签。

### 10. 测试策略

- 提及解析表驱动测试覆盖用户/智能体、单个/多个、重名、未知、自引用、重复。
- 调度器单元测试使用假执行器和虚拟时钟，覆盖并发上限、并行/串行、再触发、插话、停止、保护、恢复。
- 集成测试用五个假智能体完成分派、并行、辩论和收敛，并验证用户中途消息影响下一轮上下文。
- Playwright 团队冒烟测试覆盖创建团队、发送任务、等待收敛、打开产出物。
- 真实运行时手工验收至少跑通一次五成员头脑风暴和一次中途插话。
- 回归单智能体现有 22 个测试和 E2E，确认执行器抽取没有行为变化。

## Risks / Trade-offs

- [执行器抽取回归] 改动单智能体核心路径 → 分步抽取、保持公共 API、以现有测试和 E2E 守护。
- [并发竞态] 多运行同时更新会话与回合 → 每个会话串行状态转换、数据库事务、回合事件作为事实来源。
- [无限互 @] 成员互相提及可能产生大量运行 → 跳数、轮次、重复抑制、A-B-A 和预算共同限制。
- [上下文膨胀] 团队消息和成员结果快速膨胀 → 确定性结构化压缩，保留任务、未决问题、决策和产出物路径。
- [运行时能力差异] 部分 CLI 不支持运行中追加 → 立即插话降级为排队并显示原因，不修改适配器能力。
- [收敛质量不稳定] 指挥者可能过早或空泛收敛 → 内置协议要求结构化字段；收敛产出物单独保存，便于验证。
- [模板自动创建] 自动创建五个角色可能产生用户未预期的智能体 → 仅在用户选择模板并选择运行时后创建，创建结果在保存前可编辑/移除。

## Migration Plan

1. 在 SQLite 迁移中新增团队、成员、提及、回合和事件表，并给运行表增加可空 `team_turn_id`。
2. 增加会话 `interjection_mode`，默认 `queue`；单智能体会话无需回填。
3. 现有单智能体会话继续走 `RunService`；团队会话走 `TeamOrchestrator`。
4. 部署后首次打开团队功能时校验现有智能体/运行时引用；失效引用显示修复入口，不自动删除数据。
5. 回滚时保留新增表，不降级删除用户数据；旧版本忽略这些表。
