# Spec Delta

## Purpose

定义团队回合如何排队、并发、等待、介入和收敛，并通过可配置的保护阈值避免无限互 @、重复调用和成本失控。

## ADDED Requirements

### Requirement: 团队回合队列

本要求为强制要求（MUST）。

每个团队会话必须维护独立的调度队列。同一智能体同一时刻只能处理一个运行；同一会话的多个运行必须按队列和并发上限调度，不得因 UI 操作重复入队。

#### Scenario: 同一智能体重复入队

- **WHEN** 同一智能体在已有运行未结束时再次被提及
- **THEN** 新任务进入队列而不并行启动
- **AND** 当前运行结束后只处理一次新任务

### Requirement: 并发上限

本要求为强制要求（MUST）。

团队会话默认最大并发运行数为 3，并允许在团队配置范围内调整。达到上限时，新运行必须排队并显示排队状态，不得静默丢弃。

#### Scenario: 五个成员同时被提及

- **WHEN** 指挥者一次性精确提及五名成员
- **THEN** 最多三个运行同时开始，其余两个排队
- **AND** 界面显示每个成员的运行或排队状态

### Requirement: 并行与串行策略

本要求为强制要求（MUST）。

团队必须支持并行和串行两种扇出策略。并行时多个成员同时开始；串行时按提及顺序执行，后一个成员必须能看到前一个成员的结果。P0 使用团队配置的默认策略，不解析自然语言指令。

#### Scenario: 并行扇出

- **WHEN** 团队默认策略为并行且指挥者提及三名成员
- **THEN** 三名成员可以同时开始运行
- **AND** 结果分别返回指挥者

#### Scenario: 串行扇出

- **WHEN** 团队默认策略为串行且指挥者按顺序提及三名成员
- **THEN** 成员按提及顺序依次运行
- **AND** 后一个成员上下文包含前一个成员的结果

### Requirement: 用户插话

本要求为强制要求（MUST）。

团队运行中用户必须能够发送消息，输入框不得被阻塞。会话级插话模式为「排队」时，消息在当前运行结束后送达；为「立即插话」且运行时支持追加输入时，消息注入当前运行并标记为已插话，否则降级为排队并明确提示。

#### Scenario: 排队插话

- **WHEN** 团队运行中用户发送一条消息且会话为排队模式
- **THEN** 消息显示为已排队
- **AND** 当前运行结束后该消息送达指定目标

#### Scenario: 立即插话降级

- **WHEN** 用户选择立即插话但运行时不支持追加输入
- **THEN** 消息转为排队并显示降级提示
- **AND** 不中断当前运行

### Requirement: 停止运行

本要求为强制要求（MUST）。

用户必须能够停止单个运行或本回合全部运行。停止后两秒内界面必须显示已停止状态，保留已产生内容，并插入说明停止目标的系统事件。其他未停止运行不得被误取消。

#### Scenario: 停止单个成员

- **WHEN** 用户在多名成员运行时停止其中一名成员
- **THEN** 只有该成员的运行被取消
- **AND** 其他成员继续运行

#### Scenario: 停止全部

- **WHEN** 用户点击全部停止
- **THEN** 本回合所有运行进入已停止状态
- **AND** 会话不再调度新的运行直到用户再次发送消息

### Requirement: 循环与成本保护

本要求为强制要求（MUST）。

团队回合必须受以下默认保护：单回合最大跳数 12、辩论最大轮次 5、单运行超时 30 分钟、重复调用抑制开启、A→B→A 连续三次且无新信息时插入收敛提示。团队 token 预算可选择配置；达到 80% 时提醒，达到 100% 时停止。

#### Scenario: 达到最大跳数

- **WHEN** 单回合调度跳数达到 12
- **THEN** 编排器停止调度并让指挥者输出阶段性总结
- **AND** 会话标记为因保护阈值收敛

#### Scenario: 重复调用抑制

- **WHEN** 同一发送者在两分钟内重复向同一目标发送高度相似且无新信息的内容
- **THEN** 该次调用被抑制
- **AND** 审计记录抑制原因

#### Scenario: 达到 token 预算

- **WHEN** 团队回合 token 使用达到配置预算的 100%
- **THEN** 所有新调度停止
- **AND** 会话显示预算耗尽与当前进展

### Requirement: 指挥者协议

本要求为强制要求（MUST）。

团队必须内置指挥者协作协议：第一轮拆解并分派，第二轮起交叉引用具体观点，至少保留反方角色，需要用户决策时精确提及用户，满足收敛条件时输出结构化总结。成员配置不得覆盖该协议。

#### Scenario: 第一轮分派

- **WHEN** 指挥者收到用户的新任务
- **THEN** 它先复述目标并拆解为可分派的子问题
- **AND** 通过精确提及分派给相关成员，而不是代替成员作答

#### Scenario: 需要用户决策

- **WHEN** 指挥者遇到无法从团队信息推断的决策
- **THEN** 它精确提及用户并提出一个具体问题
- **AND** 回合进入等待用户状态

### Requirement: 收敛与总结

本要求为强制要求（MUST）。

团队回合满足最大轮次、连续无新论据或指挥者判定收敛时，必须进入收敛状态。指挥者必须输出包含结论、关键依据、分歧与未决问题、建议下一步的 Markdown 总结，并保存为工作区 `.pizza/artifacts/` 产出物。

#### Scenario: 达到最大轮次

- **WHEN** 辩论轮次达到团队配置的最大值
- **THEN** 编排器强制进入收敛
- **AND** 指挥者输出结构化总结

#### Scenario: 保存收敛产出物

- **WHEN** 指挥者完成收敛总结
- **THEN** 总结保存到 `.pizza/artifacts/` 并出现在产出物面板
- **AND** 会话标记为已完成

### Requirement: 异常与恢复

本要求为强制要求（MUST）。

运行时失败、断线或应用崩溃时，编排器必须把受影响的运行标记为失败或中断，保留已完成成员的结果，并允许用户重试或继续收敛。不得自动重放用户未确认的运行。

#### Scenario: 成员运行失败

- **WHEN** 一名成员在团队回合中运行失败
- **THEN** 该成员标记为失败并保留错误摘要
- **AND** 其他成员结果和指挥者仍可继续处理

#### Scenario: 应用崩溃后恢复

- **WHEN** 应用在团队回合运行中崩溃后重启
- **THEN** 未完成的运行显示为中断
- **AND** 用户可以看到已完成结果并选择重试
