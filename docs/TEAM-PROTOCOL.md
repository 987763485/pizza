# 团队协作协议

本文是实现与验收共同使用的团队协议说明。行为规格以 `docs/openspec/changes/p0-team-orchestration/specs/` 为准，本文解释当前实现如何落地。

## 1. 精确提及语法

| 场景 | 语法 | 示例 |
| --- | --- | --- |
| 智能体提及成员 | `[@名称](mention://agent/<agentId>)` | `[@架构师](mention://agent/8f3c…)` |
| 提及用户 | `[@我](mention://user)` | `[@我](mention://user) 请确认范围` |

- 用户消息同时接受 chip 序列化与文本 `@名称`。
- 智能体消息只接受精确链接；普通文本 `@名称` 不会触发调度。
- 名称解析顺序：本会话参与者 → 团队成员 → 工作区全局唯一名称。
- 同名命中多个智能体时返回歧义，不猜测目标；未知目标保留原文并写系统事件。
- 同一目标去重；自身提及忽略并写 `mention_ignored` 事件。
- `message_mention` 保存目标、显示名、起止位置、原始语法与是否解析成功。

### 1.1 指令来源模式

智能体通过 `agent.instruction_mode` 选择成员运行的指令来源：

| 模式 | 字段值 | 行为 |
| --- | --- | --- |
| 自带初始 Prompt | `self` | 成员使用智能体保存的 Prompt（含团队覆盖）；指挥者只描述任务 |
| 指挥者动态下发 | `leader` | 成员忽略智能体 Prompt 与团队 Prompt 覆盖；本轮触发消息作为角色指令 |

- 只有成员运行应用该模式；指挥者始终使用自己的 Prompt 与协作协议。
- 指挥者上下文的能力目录会标注每名成员的指令来源；对「指挥者动态下发」的成员，`@` 时必须写清角色、边界、输出格式与完成标准。
- 用户直接 `@` 模式二成员时，用户消息作为本轮角色指令。
- 单智能体运行、连接测试等没有指挥者下发的场景使用可选的单智能体兜底 Prompt；留空时使用通用兜底 Prompt。

## 2. 路由矩阵

单智能体与团队两种模式的完整处理流转图见 `docs/MESSAGE-ROUTING.md`。

团队交互的核心路由是 **指挥者 → 成员 → 指挥者**：指挥者 `@` 成员时，编排器向该成员下发一个单轮任务 Prompt（目标、输入、完成标准）；成员完成后把结果交回指挥者。常规编排中，成员是否参与、参与几次、以什么顺序参与由指挥者的提及决定；用户也可以直接 `@` 成员介入。成员之间的 `@` 不直接派发，作为建议随结果回到指挥者。

参与者与 Skill 的注册方式一致：每次运行都把完整的能力目录交给指挥者，由它按任务匹配度自主决定调用时机。

| 登记字段 | 来源 | 用途 |
| --- | --- | --- |
| 名称 | `agent.name` | 精确提及与界面展示 |
| 能力描述 | `agent.description` | 指挥者判断任务是否匹配该成员 |
| 团队职责 | `team_member.role` | 本次团队中的分工与边界 |
| 指令来源 | `agent.instruction_mode` | 提示指挥者是否需要在本轮消息中写完整角色指令 |
| 运行状态 | 编排器 | 避免重复派发；指挥者据此决定等待或继续 |

| 消息来源 | 显式提及 | 调度目标 | 附加行为 |
| --- | --- | --- | --- |
| 用户 | 无 | 指挥者 | 默认入口 |
| 用户 | 指挥者 | 指挥者 | 不重复抄送 |
| 用户 | 成员 | 被提及成员 | 向指挥者写被动通知 |
| 用户 | 用户 | 无 | 回合进入 `waiting_user` |
| 成员 | 其他成员 | 不派发 | 提及作为建议随结果回到调用者/指挥者 |
| 成员 | 用户 | 无 | 回合进入 `waiting_user` |
| 成员 | 无 | 调用者 | 调用者是指挥者时回到指挥者 |
| 指挥者 | 无 | 无 | 视为本轮收敛结束 |

用户插话的目标同样按上表解析；未提及成员时送达指挥者。P0 运行时均未声明追加输入能力，插话统一排队并在当前运行结束后送达；调度事件记录 `runtime_append_unsupported`。回合处于 `waiting_user` 时，用户回复继续当前回合。

## 3. 回合状态机

```text
dispatching -> debating -> waiting_user -> debating
                     \-> converging -> completed
任何非终态 -> failed | cancelled | interrupted
```

- 终态：`completed`、`failed`、`cancelled`、`interrupted`；终态不可回到运行态。
- 非法转换被拒绝（`TEAM_TURN_TRANSITION_INVALID`），由主进程串行化写入。
- 每个回合记录调度跳数、指挥者重新发言次数、`tokens_in`、`tokens_out`、`convergence_reason` 与错误；这些计数用于观察和成本统计，不作为成员参与策略。
- `team_turn_event` 的类型包括 `turn_started`、`dispatch`、`run_started`、`run_completed`、`run_failed`、`run_cancelled`、`user_interjection`、`waiting_user`、`protection_triggered`、`converging`、`turn_completed`、`turn_failed`、`turn_cancelled`、`turn_interrupted`、`mention_ignored`、`notice`。

## 4. 队列与并发

- 每个团队会话一个串行状态机与内存队列。
- 同一智能体同时最多一个运行；重复目标在入队/启动时抑制并写 `notice`。
- 并发上限取团队 `maxConcurrency`（默认 3，范围 1–10）与全局 `maxConcurrency` 的较小值。
- `parallel`：一次提及的多个成员同时启动；`serial`：按提及顺序执行，后一个成员上下文包含前一个结果。
- 运行失败按成员隔离；其他成员继续，指挥者收到失败说明并给出阶段性总结。
- 停止单个运行只取消目标运行；停止回合取消本回合全部运行，保留已产生文本并标记 `cancelled`。

## 5. 保护与收敛

团队不设“辩论轮次”上限：辩论是否存在、何时结束，由指挥者是否继续派发决定。下表只保留防止失控的技术保护。

| 保护 | 默认 | 行为 |
| --- | --- | --- |
| 单回合跳数（防失控保护） | 团队配置，默认 64（1–100） | 达到后进入收敛 |
| 单运行超时 | 30 分钟 | 取消运行并显示超时 |
| 重复调用 | 2 分钟、相似内容 | 抑制并写 `duplicate_invocation` |
| A→B→A | 连续三次 | 写 `aba_loop` 并收敛 |
| token 预算 | 默认 0（不限） | 80% 提醒，100% 停止新调度 |

收敛时向指挥者投递“停止辩论并输出结构化总结”，要求结论、关键依据、分歧与未决问题、建议下一步。文本写入工作区 `.pizza/artifacts/team-turn-<seq>.md` 并索引到产出物面板；写入失败保留会话文本并写系统消息说明原因。

## 6. 上下文与恢复

- 系统 Prompt：成员最终生效 Prompt + 参与者能力目录（名称、能力描述、团队职责、指令来源、运行状态）+ 协作协议 + 精确提及语法。团队编排规则只注入指挥者。模式二成员改用“角色由调用者动态下发”的说明，不注入其保存的 Prompt。
- 用户 Prompt：当前任务、调用者、工作区、串行前序结果、自上次指挥者发言以来的成员摘要、压缩后的消息上下文；模式二成员额外注入「本轮角色指令」（来自触发它的指挥者或用户消息）。
- 确定性压缩保留原始任务、最近消息和产出物路径；原始消息始终保留在数据库。
- 应用重启时未完成运行标记 `failed`、未完成回合标记 `interrupted` 并写事件；不自动重放，已完成文本与产出物保留。
